# PanFind 产品愿景与使用场景

> 状态：面向近期演进的产品愿景
>
> 日期：2026-08-08
>
> 说明：本文描述 PanFind 希望帮助用户解决的问题、AI Agent 的工作方式和多存储远景。早期 MVP 的技术取舍与实现细节继续保留在 [项目设计草案](项目设计草案.md) 中。

## 1. 产品使命

PanFind 希望让 AI Agent 能够自由探索用户拥有的文件资源，而不必为每一家网盘重新实现全量遍历、分页、限流、认证和私有数据库解析。

一句话定位：

> **PanFind 是给 AI Agent 和自动化工具使用的多存储 POSIX 命名空间。**

PanFind 将不同网盘、对象存储、NAS 和本地文件系统中的文件树与元数据，映射为统一的路径、目录、文件和能力语义。用户面对的是能够理解自然语言并自由选择工具的 Agent；PanFind 位于其下方，提供快速、稳定、低侵入的文件世界索引。

## 2. 项目缘起

项目源自一次真实的百度网盘全盘查重任务。目标很简单：按照“文件大小 + 稳定指纹”找出内容完全相同的资源，估算删除一个副本后可以释放的空间。

没有统一的本地查询层时，Agent 只能递归调用百度远端目录接口。为了避免风控，当时采用单线程、低频访问：

- 扫描 1,740 个目录和 17,050 个文件；
- 发出 1,824 次远端列表请求；
- 平均请求间隔约 1.30 秒；
- 第一次扫描因远端 `dir_empty` 字段语义不可靠而漏掉目录，随后被迫重扫；
- 完整过程接近一小时；
- 最终找到 317 组重复文件，理论可释放约 29.20 GB。

但百度官方客户端已经把这批文件的路径、大小和指纹缓存在本地数据库中。只要安全地读取一次本地快照，同样的分析可以在本地快速完成，不需要 1,824 次远端请求，也不需要担心限流和验证码。

由此产生了 PanFind 的核心想法：

> **把各家存储已经拥有的文件元数据统一投影为一个可查询的 POSIX 命名空间，让每个 Agent 都不必重新扫描整个云端。**

## 3. 用户真正需要的不是文件名搜索

用户经常不知道准确名称和位置，只记得一些零散线索：内容、场景、图片、年代、大小、集数、时长、来源，甚至只是“我确定保存过”。名称还可能因为语言、别名、拼写、乱码或规避版权而被故意改变。

因此 PanFind 面向的上层入口不是一个更复杂的搜索框，而是 AI Agent。用户可以提出任意形式的搜索目标，Agent 围绕目标自由探索：

1. 使用 PanFind 浏览整个命名空间并获得结构化线索；
2. 反复调整搜索范围，不受单条查询限制；
3. 结合公开互联网资料理解文件名背后的作品和知识；
4. 编写临时脚本完成聚合、归并、格式识别或统计；
5. 在工具可用且权限允许时下载少量候选，检查内容或固定结构；
6. 交付结论、准确位置、判断依据、置信度和仍待确认的候选。

PanFind 不负责限制 Agent 只能使用元数据。它只是让 Agent 在进入昂贵的内容分析之前，先高效理解用户拥有什么。

### 3.1 搜索需求与快照新鲜度的时间互补

用户对近期主动新增、删除或移动的文件通常记忆最强，对搜索的依赖最低；用户真正需要 Agent 帮助寻找的，往往是多年积累后已经忘记名称和位置的历史文件，而这部分文件又最不可能在最近几天发生变化。搜索需求与文件变化概率因此在时间上形成互补：越需要搜索的历史存量，越适合由非实时快照稳定描述；越可能使快照暂时失真的近期变更，用户通常越清楚自己做过什么。

一份旧快照要实质性妨碍搜索，需要同时发生多件事：历史文件恰好在快照生成后被移动，用户随即忘记这次主动操作，又在下一次刷新前要求 Agent 按旧线索寻找它。这是多个低概率条件的交集，不应成为所有 Provider 持续扫描远端、追求秒级一致性的默认理由。即使极端情况发生，旧快照仍能提供文件名、原路径、大小、时间和稳定标识等线索，用户或 Agent 可以据此决定是否刷新。

因此，PanFind 将“完整但可能过时、且明确标注生成时间”的快照视为有独立价值的产品能力，而不是实时视图的降级替代。普通的历史查找、盘点、统计和聚合应直接使用最近一次成功的完整快照；只有当任务明确涉及“刚才”“今天”“最新上传”等近期状态时，Agent 才需要提示快照年龄并按需触发刷新。完整性、可查询性和新鲜度必须分别表达，不能因为某个 Provider 不具备实时通知能力，就否定其完整历史快照的搜索价值。

## 4. 典型使用场景

### 4.1 全盘查重和空间清理

用户请求：

```text
找出所有大小和校验码完全相同的文件，按可释放空间从大到小排列。
只生成报告，不要删除。
```

Agent 可以利用 PanFind 的完整文件清单，按照 `(size, hash)` 分组，输出重复数量、所有路径和理论可释放空间。之后还可以结合目录上下文判断哪一份是孤立副本、哪一份带有配套资料。

未来扩展到多个 Provider 后，同一方法还可以发现跨网盘、NAS 和本地硬盘的重复资源。

### 4.2 识别语义分类

用户请求：

```text
找出视频分类中的所有韩剧，列出剧集目录并统计总容量。
中文译名也要识别，不要只搜索“韩国”两个字。
```

Agent 先用 PanFind 枚举作品目录和剧集文件，再结合中文译名、集数、文件结构和公开资料判断作品来源。目录名没有国家标签也不应被遗漏；电影、综艺或中国翻拍版则需要排除。

### 4.3 归并分卷和逻辑资源

用户请求：

```text
我的 PS3 游戏中有哪些超过 10 GiB？游戏经常是分卷压缩的，
请按游戏归并后统计。
```

Agent 不应把 `part01` 到 `part20` 当成二十个游戏。它可以根据父目录、公共文件名前缀、分卷编号和总体积形成逻辑资源，并把不确定的混合目录单独列出。

### 4.4 识别被改写或混淆的名称

用户请求：

```text
我确定保存了《金特务》，但目录可能被写成“K忑物”“JTW”，
或者只剩“金”和几个乱码字符。请把它找出来。
```

Agent 可以综合拼音和首字母、字符残片、目录位置、集数、单集大小、媒体时长、年份和公开作品资料推断候选。必要时读取字幕、媒体标签、片头关键帧或音轨信息进行确认。

PanFind 在这里提供的是完整候选空间和快速迭代能力，而不是一条必须命中的关键词规则。

### 4.5 根据电影场景寻找作品

用户请求：

```text
我记得一部电影里有这样的场景：……。我确定电影在自己的网盘里，
但完全不记得片名。请找到它。
```

可能的探索过程包括：

1. 联网根据场景描述寻找可能的作品；
2. 用 PanFind 检查这些作品、别名或年代是否出现在网盘；
3. 若名称无法匹配，按照视频目录、时长、大小和编码形成候选；
4. 在具备内容读取能力时检查字幕、音轨或抽取关键帧；
5. 返回最可能的文件及证据。

有时 PanFind 是主要入口，有时只是中间的一次候选验证。只要它能减少远端遍历和盲目下载，就发挥了价值。

### 4.6 根据图片描述定位 PDF 页面

用户请求：

```text
我能准确描述一张图片，但只知道它出现在网盘里的某本 PDF 中。
其他信息一概不知。请找到书名和页码。
```

Agent 可以先使用 PanFind 列出 PDF，并根据大小、目录、时间和书籍集合分批筛选；随后下载候选，渲染页面缩略图、执行 OCR 或图像语义比较，逐步定位到具体文档和页码。

这个任务最终依赖内容分析，但 PanFind 能够提供完整候选集合、准确路径以及可重复的筛选过程。

### 4.7 寻找模糊记忆中的技术文档

用户请求：

```text
我要找一份约 10 MB 的 PDF，大约在 2010～2015 年保存。
内容从物理网络、以太网讲到 TCP/IP 和应用层，文件名和位置都不知道。
```

Agent 可以先以 PDF、近似大小和可用时间字段生成候选，再分析路径和文件名词汇。候选足够少时，继续下载、提取目录和全文，比较章节结构。若数据源没有可靠的“加入网盘时间”，Agent必须把这一限制说清楚，而不是拿修改时间冒充。

### 4.8 识别序号命名的 ROM 和 ISO

用户请求：

```text
我的 PS3 游戏文件夹全是序号，我自己也不知道每个序号对应什么游戏。
请识别并生成映射清单。
```

Agent 可以优先使用已有哈希匹配 Redump 等公开数据库。无法匹配时，再根据文件格式选择成本最低的内容检查方法，例如读取 ISO 内的 `PARAM.SFO`、`PS3_DISC.SFB`、Title ID 或其他平台固定头部。对于很大的镜像，应先尝试哈希、Range read 或内部目录等低成本手段，再决定是否完整下载。

### 4.9 将私人收藏与公共数据结合

用户请求：

```text
找出我收藏的国产古偶剧，结合豆瓣评分，列出超过 7 分的作品。
```

PanFind 回答用户实际拥有的作品和位置，Agent 查询公共评分并对片名、年份和版本进行归一化。这种“私人文件世界 + 公共知识”的连接，是纯网盘搜索框无法完成的。

## 5. PanFind 与 Agent 的职责边界

### PanFind 负责

- 发现并安全读取各 Provider 的元数据源；
- 构建一致、稳定、可快速遍历的命名空间；
- 统一路径、目录、大小、时间、哈希和稳定 ID 等语义；
- 明确声明每个 Provider 实际具备的能力；
- 提供适合 Agent 和脚本消费的结构化接口；
- 在刷新失败时保留上一代完整快照，不输出半棵文件树。

### AI Agent 负责

- 理解用户的自然语言目标和隐含条件；
- 自主决定搜索策略并反复调用 PanFind；
- 使用常识和互联网资料进行语义判断；
- 归并逻辑资源、计算统计并表达不确定性；
- 按需调用下载、PDF、OCR、音视频和格式分析工具；
- 在涉及大量传输、隐私披露或写操作时遵守相应权限边界。

### PanFind 不应该做

- 在核心程序中内置大模型或固定领域知识；
- 为韩剧、PS3、PDF 等每种场景分别硬编码业务逻辑；
- 假装所有 Provider 都拥有相同字段；
- 为了搜索而默认全量下载用户文件；
- 把文件管理和删除混入只读查询接口。

## 6. 统一 POSIX 中间层

长期数据流：

```text
Provider-specific data source
        ↓
Provider Adapter
        ↓
Normalized POSIX namespace
        ↓
lookup / stat / read_dir / walk / query / capabilities
        ↓
AI Agent / CLI / scripts / analyzers
```

第一阶段的 POSIX 不是可挂载文件系统，而是只读命名空间和 `stat` 语义：节点、父子关系、路径查找、目录遍历、文件元数据和稳定标识。这已经足以支撑大量发现、统计和整理任务。

未来可以按 Provider 能力逐步加入可选数据面：

- `open` 或下载；
- Range read；
- 压缩包或镜像内部目录；
- 内容指纹；
- 文本和媒体派生元数据。

这些能力应通过 `capabilities` 显式声明。百度本地数据库、夸克客户端、对象存储和 NAS 不需要被迫实现相同功能。

## 7. 当前状态

当前 `v0.1.0` 已完成百度网盘 Windows 本地数据库的只读闭环：

- 自动发现账号和 `filecache.db`；
- 读取一致的 SQLite 快照；
- 构建只读命名空间；
- 支持接近 GNU `find` 的组合查询；
- 输出路径文本和 JSON Lines；
- 提供 `schema`、`capabilities`、`explain` 和 `status`；
- 支持变化监听、完整刷新、原子 generation 切换和失败保留；
- 提供可供 Codex 使用的 `search-baidu-drive` Skill。

当前 PanFind 核心不下载或读取文件内容。Agent 可以使用环境中其他已经授权的工具完成内容探索；未来也会为合适的 Provider 增加受控内容读取接口。

## 8. 近期路线图

### 8.1 Agent 原生搜索

- 将自然语言作为主要用户入口；
- 保持 Skill 高自由度，避免把 Agent 限制成 CLI 参数翻译器；
- 让结果包含准确位置、判断依据、置信度和后续验证建议；
- 与下载、PDF、OCR、音视频和通用脚本工具形成探索闭环。

### 8.2 查重与聚合

- 哈希和大小分组；
- 理论可释放空间统计；
- 目录总容量和大文件排行；
- 分卷压缩包和剧集目录归并；
- 支持跨 Provider 查重所需的统一指纹语义。

### 8.3 夸克 Provider

- 近期 Provider 范围只包括百度网盘和夸克网盘，两者是国内最主要的两家消费级网盘；
- 百度继续使用官方客户端完整本地数据库，夸克采用远端全量扫描后由 PanFind 持久化完整快照；
- 用两种不同的数据获取路径检验统一 POSIX 模型，而不是提前设计复杂插件系统；
- 夸克的实测结论、同步边界和实现计划单独维护在 [夸克 Provider 设计草案](夸克%20Provider%20设计草案.md) 中。

### 8.4 可选内容读取

- 根据 Provider 能力提供受控下载或 Range read；
- 优先支持小文件和候选片段读取；
- 为 PDF、纯文本、媒体、压缩包和 ROM/ISO 分析提供统一入口；
- 大文件操作前暴露预计传输量，并由 Agent按任务风险决定是否需要用户确认。

### 8.5 远期多存储方向（暂不排期）

- 百度和夸克两套 Provider 稳定之前，不计划接入第三家网盘或其他存储；
- 统一模型当前只需证明本地完整数据库和远端持久化快照两种路径能够共存；
- 更多网盘、对象存储、NAS、本地目录和跨存储查询保留为长期方向，不进入近期范围；
- 后台服务或 IPC 也只在百度、夸克的真实使用需要出现后再评估。

## 9. 安全、隐私和结果可信度

- 文件名、路径、哈希和时间均属于用户敏感数据；
- PanFind 默认只读，不上传遥测，不要求账号 Cookie 或密码；
- Agent 联网核验时应优先使用作品名和派生线索，不向外部网站提交完整私人路径；
- 小候选下载可以是正常的搜索步骤，但应避免无目的地批量传输；
- 删除、移动、分享等写操作必须与搜索分离，并遵守独立授权边界；
- 字段来源和语义必须明确，缺失能力不能由看似相近的字段冒充；
- 无法唯一确定时，交付有排序的候选和证据比武断返回一个答案更可靠。

## 10. 成功标准

PanFind 的价值不以实现多少 CLI 参数衡量，而以它是否帮助 Agent 更快、更安全地解决真实问题衡量：

- 是否避免了重复的全盘远程遍历；
- 是否显著减少需要下载和人工检查的候选；
- 是否能跨不同命名和目录结构找到逻辑资源；
- 是否能完成准确的容量、查重和集合分析；
- 是否能让百度和夸克两种不同数据源接入同一套上层工作流；
- 是否在能力不足时诚实表达边界，并给出可执行的下一步。

最终，用户不需要知道文件位于哪一家存储，也不需要学习某家网盘的查询语法。他只需要告诉 Agent 自己想找什么。
