## 1. 范围和定位

PanFind 近期只支持百度网盘和夸克网盘，不计划接入第三家网盘。两者分别验证两种有代表性的数据获取路径：

- 百度从官方客户端维护的完整本地数据库加载快照；
- 夸克通过只读远端全量扫描获取元数据，再由 PanFind 持久化完整快照。

夸克 Provider 的目标不是实时挂载网盘，而是为 AI Agent 提供一份有明确生成时间、可快速查询、内部完整一致的只读 POSIX 元数据快照。

## 2. 已验证的客户端行为

### 2.1 本地持久化组成

夸克 Windows 客户端具有上传、下载和备份任务数据库，但这些 SQLite 数据库只描述传输任务，不是完整文件树。

客户端还会在 IndexedDB 中保存访问过的目录及其文件列表。实际记录包含：

- 文件 ID 和父目录 ID；
- 文件名；
- 文件或目录类型；
- 文件大小；
- 创建和修改时间；
- 分类和缩略图等辅助信息。

当前缓存中没有发现可作为内容指纹的 MD5、SHA-1 或其他哈希字段。

### 2.2 按需目录缓存

本地 IndexedDB 不是完整网盘目录树，而是按需保存客户端访问过的目录。受控实验如下：

1. 夸克网盘中已有 `E01.mkv` 至 `E06.mkv` 六个文件；
2. 桌面客户端浏览对应目录后，本地缓存出现六个文件的丰富元数据；
3. 随后从网页端向其子目录上传 `pumpkin_book.pdf`；
4. 桌面客户端停留在父目录时，本地所有缓存均没有该 PDF；
5. 进入目标目录后，PDF 立即出现在 IndexedDB 中。

这说明客户端不会递归维护全盘元数据，也不能依靠父目录页面获知其他客户端对子目录产生的变化。IndexedDB 可以作为已访问目录缓存或变化提示，但不能直接满足 `Adapter.LoadSnapshot` 的完整性约束。

### 2.3 重复记录

同一文件可能在 IndexedDB 中重复出现。实测中的六个视频经过多次剪切操作后，各自出现多份历史记录。这符合 LevelDB 追加状态和延迟压缩的行为，不能把原始出现次数解释成网盘中的文件副本数。正式实现不能依赖扫描二进制字符串并按名称去重。

## 3. 非实时快照的需求依据

非实时不等于没有搜索价值。用户对近期主动新增、删除或移动的文件记忆最强，通常不依赖 Agent 搜索；用户真正需要寻找的往往是多年积累、名称和位置已经遗忘的历史文件，而这部分文件在最近几天发生变化的概率最低。

旧快照要实质性妨碍一次历史搜索，需要同时满足：历史文件恰好在快照后被移动，用户随即忘记这次主动操作，又在下一次刷新前要求 Agent 按旧线索寻找。这个低概率交集不值得成为持续全盘扫描和追求秒级一致性的默认理由。

因此，夸克 Provider 优先保证：

1. 快照覆盖完整目录树；
2. 快照内部一致，失败时不发布半棵树；
3. 查询只访问本地持久化数据；
4. 明确展示快照生成时间和年龄；
5. 由用户或计划任务按需执行下一次全量刷新。

完整需求论证见 [产品愿景与使用场景](产品愿景与使用场景.md#31-搜索需求与快照新鲜度的时间互补)。

## 4. 目标数据流

```text
夸克只读远端目录接口
        ↓
递归分页扫描器
        ↓
PanFind 持久化元数据数据库
        ↓
Quark Provider Adapter
        ↓
不可变 POSIX Snapshot
        ↓
AI Agent / CLI / scripts
```

远端是最终权威来源；PanFind 自己的数据库是最近一次成功扫描的持久化镜像；客户端 IndexedDB 只作为可选变化线索，不作为完整性依据。

## 5. 首次初始化和全量刷新

首次同步从根目录开始，以广度优先或深度优先方式递归处理所有目录：

1. 分页读取一个目录的全部直接子项；
2. 将新发现的目录加入持久化扫描队列；
3. 将文件和目录写入 staging generation；
4. 保存分页和目录进度，允许进程退出后继续；
5. 对请求执行限速、退避和有界重试；
6. 只有扫描队列清空且所有分页成功时，才原子发布新 generation；
7. 扫描失败或取消时，继续提供上一代完整快照。

全量刷新不应在每次查询或程序启动时隐式发生。它是用户明确触发或计划任务触发的维护动作，扫描期间查询继续使用旧快照。

## 6. 非实时一致性模型

没有远端 change feed 时，其他客户端产生的变化无法被及时发现。第一版明确采用非实时模型：

- 普通查询直接使用最近一次成功的完整快照；
- 用户需要时手动执行全量刷新；
- 可选地按日或按周计划全量刷新；
- 状态输出展示最近成功同步时间、快照年龄、同步进度和最近错误；
- 任务明确涉及“刚才”“今天”“最新上传”等近期变化时，Agent 可以建议先刷新；
- 不因快照较旧而阻塞普通历史搜索。

本地 IndexedDB 后续可以用于发现本机刚访问或操作过的目录，但它只能把目录标记为可能变化，不能直接证明完整的新增、移动或删除。任何局部刷新都必须保持快照完整性语义，不能把部分缓存直接合并后冒充全盘最新状态。

## 7. POSIX 字段映射

夸克远端文件 ID 是字符串，而当前 `namespace.NodeKey.ID` 是 `int64`。Provider 自己的数据库应维护远端 ID 到稳定内部 `int64` 的唯一映射，不需要扩大核心命名空间类型。

初始能力预期为：

```text
size=true
modified_at=true
created_at=true
added_at=false
hash=false
stable_id=待验证
incremental_hint=false
```

文件移动和重命名前后的远端 ID 稳定性必须经过真实测试后，才能把 `stable_id` 声明为 `true`。缺失哈希时保持 `nil`，不能用其他字段冒充内容指纹。

## 8. 建议的持久化状态

Provider 自有数据库至少需要表达：

- `nodes`：当前已发布 generation 的文件和目录；
- `remote_ids`：远端字符串 ID 与内部 `int64` ID 的稳定映射；
- `sync_runs`：每次扫描的状态、起止时间和错误；
- `crawl_queue`：待扫描目录、分页位置和重试状态；
- `staging_nodes`：尚未发布的新 generation；
- `dirty_dirs`：来自本地缓存的可选变化提示。

具体表结构应在远端列表字段和分页语义验证完成后确定，不应提前绑定未经验证的客户端内部字段。

## 9. 下一步只读验证

正式实现前先完成小范围技术验证：

1. 能否稳定分页读取根目录；
2. 能否递归读取多层子目录；
3. 单目录超过一页时是否无遗漏、无重复；
4. 文件和目录移动、重命名后的 ID 是否稳定；
5. 授权过期后的续期行为；
6. 请求限流、超时和重试边界；
7. 是否存在可选的 cursor 或 change feed；
8. 扫描中断后是否能从持久化队列安全继续。

只有这些验证通过，才开始实现 `internal/quark`。第一版只承诺可重复生成完整快照，不承诺实时同步。

## 10. 非目标

第一版夸克 Provider 不做：

- 秒级跨设备同步；
- 上传、删除、移动或重命名；
- 用客户端零散缓存冒充完整目录树；
- 为获取哈希而下载全部文件；
- 在每次查询时访问远端；
- 第三家网盘或通用插件系统。
