# PanFind（盘寻）项目设计草案

> 状态：可运行的百度只读原型；已提供稳定同步和多账号选择闭环
> 日期：2026-08-08
> 说明：本文档整理自项目前期讨论和对本机百度网盘客户端的只读探索，用于后续正式开发时建立共同上下文。它不是 README，也不代表所有技术选型已经最终确定。

## 1. 项目缘起

百度网盘等消费级云盘能够按照文件名进行普通搜索，但缺乏类似 Linux `find` 的文件元数据查询能力。例如，用户通常无法直接完成以下查询：

```bash
find / -type f -size +1G
find / -type f -iname "*.exe"
find /资料 -type f -mtime -365
find / \( -iname "*.iso" -o -iname "*.zip" \) -size +500M
```

文件数量较少时，按照名称搜索基本够用。文件积累到几万甚至几十万个以后，用户经常只记得文件的部分特征，而不记得准确名称：

- 大致大小；
- 文件扩展名；
- 大致存入网盘或修改的时间；
- 所在目录的大致位置；
- 同一目录中的文件数量；
- 整个目录的大致总大小。

影视资源是一个典型例子。同一部电视剧可能使用中文译名、英文名、韩文名或不同地区的译名，名称关键词很难稳定命中；但用户可能记得它由十几到二十几集组成、每集约 800 MB～2 GB、存入时间大约在某一年。元数据组合查询在这种情况下比模糊文件名搜索更可靠。

PanFind 希望补上这一层能力：把封闭在官方客户端或云端接口中的文件元数据，投影为一个统一、只读、类似 POSIX 文件命名空间的结构，并在其上提供可组合、可脚本化的查询语言。

## 2. 项目定位

一句话定位：

> PanFind（盘寻）是面向云盘的 POSIX 风格文件元数据查询工具。

英文描述暂定为：

> POSIX-style metadata search for cloud drives.

项目首先面向熟悉命令行、脚本和文件系统语义的极客用户。CLI 是正式且稳定的产品接口，图形界面不是第一阶段目标。后续可以通过 AI Skill 把自然语言编译成同一套确定性查询，使不会写命令的用户也能使用。

PanFind 不是新的百度网盘客户端，也不负责替代官方客户端。官方客户端继续完成登录、远端同步、上传和下载；PanFind 只负责读取元数据、构建命名空间和执行查询。

## 3. 核心原则

### 3.1 只读和低侵入

- 默认只读官方客户端的本地数据库。
- 不向官方数据库添加表、索引或触发器。
- 不修改官方客户端配置和系统设置。
- 不注入官方客户端进程。
- 不解析和篡改 SQLite WAL。
- 不要求用户提供 BDUSS、Cookie 或账号密码。
- PanFind 退出或删除后，不应影响官方客户端继续工作。

### 3.2 CLI 是事实标准

- 查询语义由解析器和 Query AST 定义。
- 人工输入命令、脚本调用、GUI 和 AI Skill 最终都进入同一个 AST 和执行器。
- AI 不是查询引擎，只是自然语言到确定性命令或 AST 的编译器。
- 查询命令应当透明、可复制、可保存、可重复执行。

### 3.3 稳定优先于绝对实时

- 允许查询结果相对官方客户端滞后，目标延迟不超过约 1 秒。
- 查询可以看到旧但完整的快照，不能看到更新了一半的目录树。
- 同步失败时保留上一代完整快照，并明确暴露陈旧状态和错误原因。
- 不以错误字段冒充缺失字段，例如不能拿修改时间冒充加入网盘时间。

### 3.4 先解决一个窄问题

第一阶段只做好百度网盘的本地元数据查询。以下内容均不应进入首个 MVP：

- 上传和下载；
- 网盘文件管理；
- 文件内容搜索；
- 视频预览；
- 网盘挂载；
- GUI；
- AI 模型集成；
- 夸克适配；
- 删除、移动、重命名等写操作。

### 3.5 技术选型

核心程序确定使用 **Go 1.24** 实现，采用单一 Go module 和 Windows/macOS 原生 CLI。选择 Go 的主要原因是项目以 AI 辅助开发为主，维护者已经熟悉 Go，能够直接审查和接管生成代码；同时本项目的主要挑战是 SQLite 一致性读取、查询语义和快照边界，而不是需要手工内存管理的极限性能场景。

工程上通过以下约束保证长期可维护性：

- 快照只能由 builder 构造，发布后视为不可变；
- 使用原子指针一次性切换查询可见 generation；
- 查询 Parser、AST、能力检查和执行器保持分层；
- 使用 `go test`、表驱动测试、模糊测试和 `go test -race` 验证正确性；
- 用 10 万和 100 万节点合成数据实测内存与 GC，不提前根据语言印象做优化；
- 优先使用标准库和少量成熟依赖，避免不必要的框架和复杂泛型。

## 4. 项目名称

当前暂定名称为 **PanFind**，中文名为 **盘寻**。

选择理由：

- `Pan` 在国内语境中容易联想到网盘；
- `Find` 直接对应 Linux `find`；
- 不绑定百度，未来可以支持夸克和其他数据源；
- 名称短，适合作为命令名；
- `panfind baidu:/ ...` 的命令形式自然。

初步检查时，`lenovobenben/panfind` 尚不存在，Go module 生态中也没有形成同名云盘查询工具的品牌占用。GitHub 上存在少量同名小仓库，但没有形成云盘文件查询工具的品牌占用。该检查不等同于商标检索，正式发布前仍可复核。

## 5. 用户场景

### 5.1 按大小寻找文件

```bash
panfind baidu:/ -type f -size +1G
```

### 5.2 查找某种扩展名

```bash
panfind baidu:/ -type f -iname "*.exe"
panfind baidu:/ -type f \( -iname "*.mkv" -o -iname "*.mp4" \)
```

### 5.3 按时间范围查找

```bash
panfind baidu:/ -type f -newermt 2025-01-01 ! -newermt 2026-01-01
```

时间查询必须说明使用的是修改时间、创建时间、加入时间还是 PanFind 首次观察时间。数据源没有相应字段时，命令应报告能力不支持。

### 5.4 根据文件轮廓寻找忘记名称的资源

```bash
panfind baidu:/ \
  -type f \
  \( -iname "*.mkv" -o -iname "*.mp4" \) \
  -size +800M \
  -size -2G
```

### 5.5 目录聚合查询（后续扩展）

标准 GNU `find` 不擅长表达目录聚合条件，但这是云盘整理的重要需求，可以作为 PanFind 扩展语法：

```bash
panfind baidu:/ \
  -type d \
  -children-type video \
  -children-count +15 \
  -total-size +20G \
  -total-size -40G
```

聚合条件可以用于寻找电视剧、课程、分卷压缩包和大型软件目录。

## 6. 已验证的百度网盘本地数据

### 6.1 客户端兼容性基线

PanFind 读取的是百度网盘桌面客户端的内部数据库，而不是稳定的公开协议。因此，项目与客户端生成的 `filecache.db` 路径、表结构和字段语义存在直接的版本绑定关系。兼容性结论必须同时记录客户端平台和版本，不能笼统地写成“支持百度网盘”。

| 平台 | 百度网盘客户端版本 | 验证日期 | 验证状态 |
| --- | --- | --- | --- |
| Windows amd64 | `8.6.8.102` | 2026-08-13 | 开发基线；已使用真实本地数据库验证账号发现、快照加载和查询 |
| macOS Intel amd64 | `8.7.0 (461)` | 2026-08-19 | 已使用真实本地数据库验证账号发现、快照加载和查询 |
| macOS Apple Silicon arm64 | 未记录 | — | 仅通过原生 ARM64 CI，尚未使用真实客户端数据库验证 |

若后续客户端升级导致 `.db` 路径、结构或字段语义变化，应先使用对应平台已验证的客户端版本复现当前基线，再为新版本增加适配和兼容测试。不要在未验证新数据库的情况下覆盖历史记录；应在表中新增一条版本记录。

本基线对应 PanFind `v0.3.0`（提交 `3bd1937`）。未来排查兼容性回归时，应同时记录 PanFind 版本或提交、客户端版本、操作系统和实际 schema。

### 6.2 数据库位置

当前 Windows 客户端的主要文件元数据数据库位于：

```text
%APPDATA%\baidu\BaiduNetdisk\module\BrowserEngine\users\<account-id>\filecache.db
```

macOS 客户端使用兼容的 `file_meta` 表，主要数据库位于：

```text
~/Library/Application Support/com.baidu.BaiduNetdisk-mac/<account-id>/filecache.db
```

macOS 客户端为路径唯一索引声明了私有的 `baidunetdisksort` collation。PanFind 不尝试复刻未知排序语义，而是对 `file_meta` 明确使用 `NOT INDEXED` 做只读全表扫描；这既避开私有 collation，也与完整快照加载的访问模式一致。

实际实现必须通过目录发现账号，不能硬编码具体账号目录。需要考虑多账号和未来客户端版本改变路径的情况。

### 6.3 `file_meta` 表

本机当前版本的核心表结构为：

```sql
CREATE TABLE file_meta(
  id INTEGER PRIMARY KEY,
  fid INTEGER,
  parent_path TEXT,
  server_filename TEXT,
  file_size INTEGER,
  md5 TEXT,
  isdir BOOLEAN,
  category INTEGER,
  server_mtime INTEGER,
  local_mtime INTEGER,
  reserved1 TEXT DEFAULT '',
  reserved2 TEXT DEFAULT '',
  reserved3 TEXT DEFAULT '',
  reserved4 TEXT DEFAULT '',
  reserved5 TEXT DEFAULT '',
  reserved6 INTEGER DEFAULT 0,
  reserved7 INTEGER DEFAULT 0,
  reserved8 INTEGER DEFAULT 0,
  reserved9 INTEGER DEFAULT 0
);
```

数据库中还发现：

- `file_meta_content`；
- FTS5 表 `full_text_search_file_v2`，索引 `server_filename` 和 `parent_path`；
- `sync_cursor`；
- `version`；
- 自定义排序规则 `baidunetdisksort`。

这些事实说明官方客户端确实维护了可供本地浏览和名称/路径检索使用的文件元数据缓存。但 PanFind 不应依赖官方 FTS 来完成高级查询，核心数据仍应来自 `file_meta` 的一致性快照。

### 6.4 当前样本规模和读取性能

在开发机当前账号上，探索时统计到：

- 节点总数：18,706；
- 文件：16,987；
- 目录：1,719；
- 大于 1 GiB 的文件：2,934；
- `.exe` 文件：43；
- 修改时间在 2025 年之后的文件：4,510；
- FTS 行数与节点总数相同。

只读扫描全部 18,706 行相关元数据的耗时：

- 中位数约 32.57 ms；
- 最快约 31.37 ms；
- 最慢约 44.07 ms。

因此在当前规模下，变化后重新读取数据库并构建完整快照是可行的。稳定同步的第一版直接采用全量刷新，以换取更少的状态、更清晰的失败边界和更低的实现风险。只有真实规模无法满足约一秒的刷新目标时，才考虑行指纹和增量应用。

### 6.5 SQLite 读取注意事项

官方数据库使用 WAL 模式，运行时需要关注：

```text
filecache.db
filecache.db-wal
filecache.db-shm
```

监控应覆盖数据库、WAL、SHM 和父目录，因为数据库文件可能被替换，而不是始终原地修改。当前简单实现采用 100 ms 轮询：数据库和 WAL 比较大小与修改时间；SHM 只比较存在性和大小，因为 SQLite 的只读连接本身也可能更新 SHM 修改时间，不能让 PanFind 的读取触发自己的下一轮刷新。

读取时应使用 SQLite 只读连接和一致性事务。由于官方数据库定义了自定义排序规则 `baidunetdisksort`，某些查询可能报错：

```text
no such collation sequence: baidunetdisksort
```

可评估的规避方式包括：

- 查询 `file_meta NOT INDEXED`；
- 在连接中注册兼容的 `baidunetdisksort` collation；
- 明确选择不会触发相关索引的查询计划。

不能假设任何普通 `SELECT` 都不会触发自定义 collation。

当前 Go 实现选用无 CGO 的 `modernc.org/sqlite`，固定在支持 Go 1.24 的版本。生产读取使用 `mode=ro`、`query_only` 和只读事务，扫描 `file_meta` 时显式使用 `NOT INDEXED`，既避免修改官方数据库，也避免查询计划误用带有 `baidunetdisksort` 的索引。

### 6.6 时间字段的限制

当前 `filecache.db` 没有覆盖全部文件的通用 `server_ctime` 或可靠的“加入网盘时间”。`reserved6`～`reserved9` 也不能当作时间戳使用。

在其他局部数据库中观察到过创建时间，例如：

- 图片数据库中的 `ctime`；
- 消息附件表中的 `server_ctime`；
- 上传历史中的操作时间。

这些字段只覆盖特定数据子集，不能拼成完整的全盘创建时间。

因此第一版本地数据源能够可靠提供的是：

- 文件名和父路径；
- 文件或目录类型；
- 文件大小；
- `server_mtime`；
- `local_mtime`；
- MD5（存在时）；
- 分类字段；
- 百度文件 ID。

工具安装后可以记录新出现节点的 `first_seen_at`，但必须明确：

- 它只是 PanFind 首次观察时间；
- 它不能还原工具安装以前的加入时间；
- 首次初始化时，所有历史文件不能被误认为同时加入网盘。

未来如果通过官方 API 获得 `server_ctime`，必须记录字段来源和语义，不能与本地推断值混在一起。

### 6.7 Go 原型规模基线

2026-08-08 在 Windows、Go 1.24、Intel Core i5-13400F 上使用匿名合成数据执行一次基准，结果如下：

| 场景 | 耗时 | 单次分配 | 分配次数 |
| --- | ---: | ---: | ---: |
| 构建 10 万文件快照 | 62.48 ms | 38.38 MB | 800,568 |
| 构建 100 万文件快照 | 0.990 s | 441.06 MB | 8,008,268 |
| 构建 1,000 层深目录快照 | 11.73 ms | 15.01 MB | 4,040 |
| 在 10 万节点中查询约 5 万个结果并收集到切片 | 34.16 ms | 46.10 MB | 300,072 |
| 在 10 万节点中查询约 5 万个结果并流式消费 | 19.95 ms | 4.40 MB | 300,001 |

这些数字是 benchmark 的 `B/op`，合成文件带有修改时间、哈希和分类字段；100 万节点的实际峰值还需要加上输入数据本身。查询主路径逐条输出，和兼容用的结果切片收集方式相比，单次分配从约 46.10 MB 降至 4.40 MB，耗时从约 34.16 ms 降至 19.95 ms。

每个快照只描述一个 provider/account，内部索引因此使用 `int64` 节点 ID，而不是在多张 map 中重复保存包含 provider、account 两个字符串的完整 `NodeKey`；路径反向索引也直接并入内部节点记录。构造器和所有按键访问接口都会校验 provider/account 作用域，公开 API 仍使用完整 `NodeKey`。与优化前的同口径基线相比，10 万节点快照分配从 73.19 MB 降至 38.39 MB，100 万节点从 891.31 MB 降至 441.05 MB。

流式查询仍有约 30 万次小对象分配，主要来自 `Snapshot.Node` 为三个可选元数据指针做的防御性复制。它保证调用方不能通过结果修改快照。对真实约 1.8 万节点和现代桌面内存环境而言，这个成本可以接受，不再为消除这些分配引入额外元数据池或视图层。

曾经验证过密集节点表、连续元数据池和路径字符串池，能够进一步降低百万节点内存与分配次数，但会显著增加快照内部复杂度。这些实验已保留在 Git 历史中，当前实现主动回到简单的 `int64 ID` 索引和不可变节点副本。除非真实用户出现 OOM、明显 GC 停顿或无法满足一秒刷新目标，否则不再继续内存优化。

结论是：当前结构在 1.8 万真实节点和 10 万合成节点下足够快，百万节点约 441 MB、约 1 秒的构建成本也属于可接受的规模上界。下一步进入稳定同步：变化监听、合并刷新、原子 generation 切换，以及失败时保留上一代完整快照。

Parser 和 `-printf` 还分别完成了约 128 万次和 148 万次短时 fuzz 执行，未发现 panic 或崩溃。当前另有 22 个固定 GNU `find` 差分案例，覆盖类型、名称、路径、大小单位、时间、深度和布尔优先级；fuzz 与差分测试互补，前者寻找崩溃输入，后者固定兼容语义。

## 7. POSIX 风格命名空间

### 7.1 目标

PanFind 不需要实现一个完整可挂载的 POSIX 文件系统。第一阶段只模拟只读文件命名空间和 `stat` 所需的元数据语义：

- 节点；
- 父子关系；
- 路径查找；
- 目录遍历；
- 文件元数据；
- 稳定的节点标识。

不需要模拟文件内容、页缓存、文件锁、权限修改、硬链接和完整原子写语义。

### 7.2 建议的数据结构

```go
type Namespace struct {
    root     NodeID
    nodes    map[NodeID]Node
    children map[NodeID][]NodeID
}

type Node struct {
    Provider    ProviderID
    Account     AccountID
    ID          NodeID
    ParentID    NodeID
    Name        string
    Kind        NodeKind
    Size        uint64
    ModifiedAt  *time.Time
    CreatedAt   *time.Time
    AddedAt     *time.Time
    FirstSeenAt *time.Time
    Hash        *string
    Category    *int32
}
```

百度的 `fid`/`fs_id` 可以作为数据源内部稳定标识，但统一层应当把数据源、账号和节点 ID 组合起来，避免多账号和多网盘冲突。

不建议使用递归 `Box<Node>` 直接表示树。基于节点表和父子索引的结构更适合：

- 移动和重命名；
- 完整代际重建和原子替换；
- 快速通过 ID 查找；
- 多代快照切换；
- 以后增加并发查询。

### 7.3 基础接口

```text
lookup(path)
stat(node_id)
read_dir(node_id)
walk(node_id)
path_of(node_id)
apply_batch(changes)
```

### 7.4 能力声明

不同数据源拥有的字段不同，适配器必须声明能力：

```text
supports_size
supports_modified_at
supports_created_at
supports_added_at
supports_hash
supports_stable_id
supports_incremental_hint
```

查询执行前先做能力检查。字段缺失时应明确报错或要求用户选择降级语义，不能静默替换。

## 8. 数据源适配器

核心查询引擎不能硬编码百度字段。建议抽象为：

```text
Provider Adapter
├── discover_accounts()
├── inspect_schema()
├── load_snapshot()
├── watch_change_hints()
├── fingerprint(node)
└── capabilities()
```

长期的数据流为：

```text
百度本地数据库 ─────> Provider Adapter ─> 标准化命名空间 ─> 查询引擎
其他 Provider 数据源 ─┘
```

第一阶段只实现 `baidu-local-db`，本文继续记录百度只读 MVP 的实现和验证。夸克采用不同的数据获取与持久化策略，单独见 [夸克 Provider 设计草案](夸克%20Provider%20设计草案.md)，不在本文混写其同步模型。

## 9. 同步和一致性模型

### 9.1 启动阶段

每次 PanFind 启动时执行一次完整刷新：

1. 发现已安装客户端和账号数据库；
2. 检查数据库版本和表结构；
3. 读取一致性快照；
4. 构建完整命名空间；
5. 原子发布第一代可查询快照；
6. 开始监听变化提示。

第一版在启动和检测到变化时都构建完整快照。当前真实数据约 1.8 万节点，这种实现足够快，也避免维护增量状态。以后只有在实测不能满足刷新目标时才引入差异更新。

### 9.2 运行阶段

文件变化提示只表示“某些数据可能改变”，不能直接当作数据库事务日志。第一版算法：

1. 轮询 `filecache.db`、WAL、SHM 及其父目录的文件签名；
2. 第一次事件触发一个最长约 1 秒的刷新窗口；
3. 合并窗口内的突发事件，但不能因为事件持续到来而无限推迟刷新；
4. 打开新的 SQLite 只读一致性事务；
5. 读取全部行并构建下一代完整命名空间；
6. 完成结构和路径校验；
7. 原子切换查询可见快照。

状态机可以表示为：

```text
CLEAN -> DIRTY -> REFRESHING -> CLEAN
```

查询始终读取当前已发布快照：

- 扫描期间继续读取旧快照；
- 完整新快照构建完成后一次性切换；
- 不让查询观察到半更新状态。

### 9.3 失败策略

遇到以下问题时，保留上一代完整快照：

- 数据库暂时被占用；
- SQLite 读取失败；
- 自定义 collation 问题；
- 表结构变化；
- 文件监控溢出；
- 数据校验失败。

随后重试，并通过状态命令暴露错误。第一版的每次刷新都是完整重建；因为新快照在成功前不会发布，所以失败不会污染当前查询视图。

### 9.4 状态可观测性

建议提供：

```bash
panfind status
panfind status --json
```

至少输出：

- 数据源和账号；
- 适配器版本；
- 当前 generation；
- 节点数、文件数和目录数；
- 最近成功同步时间；
- 当前快照年龄；
- 当前状态；
- 最近错误；
- 当前数据源能力。

官方客户端关闭后，本地数据库可能不会反映云端其他设备产生的新变化。PanFind 必须展示数据新鲜度，不能宣称它拥有实时远端视图。

## 10. 查询语言

### 10.1 第一阶段兼容子集

建议第一版支持有实际价值的 GNU `find` 子集：

- `-type`；
- `-name`、`-iname`；
- `-path`、`-ipath`；
- `-size`；
- `-mtime`；
- `-newermt`；
- `-maxdepth`、`-mindepth`；
- `-a`、`-o`、`!`；
- 括号；
- `-print`；
- `-printf`。

不应在本地数据源没有完整创建时间时宣称支持准确的 birth/creation time 查询。

当前 Go 原型已经实现：`-type`、`-name`、`-iname`、`-path`、`-ipath`、`-size`、`-mtime`、`-newermt`、`-mindepth`、`-maxdepth`、隐式/显式 AND、OR、`!`、括号、终端位置的 `-print` 和 `-printf`。Parser 使用递归下降并遵循 `!` 高于 AND、AND 高于 OR 的优先级；深度选项当前要求放在查询谓词之前。`-printf` 首版支持 `%p`、`%f`、`%s`、`%y`、`%T+`、`%%` 以及常用转义。尚未实现的谓词或格式必须明确报错，不能被当成普通文本忽略。

### 10.2 PanFind 扩展

在标准子集稳定后，可以增加云盘专用谓词：

- `-added-after`、`-added-before`；
- `-first-seen-after`；
- `-hash`；
- `-category`；
- `-total-size`；
- `-children-count`；
- `-children-type`；
- provider/account 筛选。

扩展谓词必须与标准谓词清晰区分，并在 `--help` 和 `schema --json` 中说明字段来源与语义。

### 10.3 输出和管道

首版至少支持：

- 默认路径文本输出；
- `-printf`；
- JSON Lines；
- 稳定排序选项；
- 退出码区分无结果、查询错误和数据源错误。

这样可以与现有工具组合：

```bash
panfind baidu:/ -type f -size +1G --json | jq ...
panfind baidu:/ -type f -iname "*.mkv" | sort
panfind watch baidu:/ -type f -iname "*.mkv" --json
panfind accounts --json
panfind baidu:/ --account <account-id> -type f -size +1G
```

`awk`、`sort`、`head`、`wc`、`uniq` 等只处理查询结果流，不需要访问虚拟文件内容。第一阶段无需自行重写所有 Unix 工具。

`watch` 是第一版最小的长期运行入口。它在前台维持一个账号同步会话，首代和每次成功发布新 generation 后重新执行同一条查询；文本模式通过 stderr 报告 generation 和匹配数，JSON Lines 的每条结果包含 `generation`。Ctrl+C 正常结束。它不是后台服务，不提供 IPC，也不保存第二份持久化缓存。

当前原型固定退出码契约：`0` 表示成功且查询至少有一个结果，`1` 表示合法查询无结果，`2` 表示命令或查询语法错误，`3` 表示数据源错误，`4` 表示输出错误。下游命令正常提前关闭管道仍返回 `0`。该契约也由 `schema --json` 暴露，供脚本和 Agent 使用。

### 10.4 不安全或语义不完整的命令

MVP 不支持：

- `-delete`；
- 任意 `-exec`；
- `rm`、`mv`、`cp`；
- 对远端内容执行 `cat` 或 `grep`；
- 未下载文件的内容搜索。

## 11. 查询实现

内部执行链建议为：

```text
命令文本 -> Parser -> Query AST -> 能力检查 -> 命名空间遍历 -> 输出
```

项目确定使用 Go 实现。首版自行实现较小的 GNU `find` 兼容子集：CLI 外壳只负责识别 PanFind 子命令和全局选项，`-type`、`!`、括号等查询 token 原样交给独立的递归下降解析器，生成 Query AST 后再执行能力检查和求值。

查询兼容性通过差分测试保证：当前测试会在临时目录创建真实文件树，再从同一目录构建 PanFind 快照，分别交给 GNU `find` 和 PanFind 并比较支持范围内的结果。这样既不把真实操作系统遍历逻辑带入虚拟命名空间，也能让兼容边界保持明确和可验证。

## 12. AI Skill

AI 能力不内置在核心可执行文件中。PanFind 应先提供稳定的机器接口：

```bash
panfind capabilities --json
panfind schema --json
panfind explain <query>
panfind query <query> --json
```

当前 Go 原型已提供 `capabilities --json`、`schema --json`、`explain ... --json` 和显式 `query ... --json`。`schema` 描述谓词、运算符、深度选项和输出动作，`explain` 输出解析后的规范化 AST；两者都不访问用户数据库，适合 Agent 在执行查询前做确定性规划和校验。

随后可以在仓库中提供 Codex、Claude 或其他 Agent 可使用的 Skill。建议流程：

```text
用户自然语言
    -> Skill 获取 capabilities/schema
    -> 生成命令或 Query AST
    -> Parser 和能力检查
    -> 执行只读查询
    -> 展示实际命令并总结结果
```

例如：

```text
用户：找出我在 2025 年左右保存的电视剧，每集大概 800M 到 2G，只看 mkv 和 mp4。
```

Skill 可以生成：

```bash
panfind baidu:/ \
  -type f \
  \( -iname "*.mkv" -o -iname "*.mp4" \) \
  -size +800M \
  -size -2G
```

如果当前数据源不支持 `added_at`，Skill 必须说明限制并询问是否改用修改时间或 `first_seen_at`，不能自行替换。

只读查询可以允许 Agent 自动执行。未来若出现写操作，必须与查询接口隔离，并设置明确的人工确认边界。

## 13. 多网盘和对象存储

### 13.1 夸克

百度和夸克是近期仅支持的两家核心网盘。本文聚焦百度；夸克的客户端实测、需求依据、远端扫描和持久化快照方案单独见 [夸克 Provider 设计草案](夸克%20Provider%20设计草案.md)。

### 13.2 对象存储

原生对象存储通常提供 key、size、etag、last modified 和 prefix，并不提供完整 POSIX 语义。按照大小、时间和复杂组合查询时，原生接口往往仍需要遍历对象列表，或依赖额外清单和分析服务。

JuiceFS 一类系统通过独立元数据层将对象数据映射为目录、inode 和 POSIX 操作。PanFind 与其理念相似，但范围小得多：PanFind 只建立只读元数据命名空间，不承担文件内容存储和完整文件系统一致性。

长期可以增加对象存储适配器，但不应让它影响百度 MVP 的简洁性。

## 14. 现有开源项目调研

截至 2026-08-08，没有发现与 PanFind 目标等价的开源项目。最接近的项目包括：

### 14.1 OpenList

- 支持百度网盘；
- 能递归建立索引；
- `SearchNode` 包含 `parent`、`name`、`is_dir`、`size`；
- 实际查询接口主要是父路径、名称关键词和文件/目录 scope；
- 没有 GNU `find` 谓词、时间范围、复杂布尔表达式和本地官方数据库适配。

OpenList 已经完成了“遍历云盘并建立名称索引”的部分工作，是重要参考，但产品目标和认证路径与 PanFind 不同。

### 14.2 BaiduPCS-Go

- 仿 Linux Shell；
- 支持浏览、上传、下载、目录树和搜索；
- README 明确说明搜索是“按文件名搜索”，并且不搜索目录；
- 不提供通用元数据谓词。

### 14.3 BaiduPCS-Rust

- 活跃的 Rust 第三方客户端；
- 支持全局搜索；
- 当前搜索实现主要把 `key`、`page`、`num`、`recursion` 传给百度 `/api/search`；
- 不提供 POSIX 元数据查询层。

### 14.4 MongoDB 文件列表脚本

存在抓取百度全盘文件信息到 MongoDB、按照 MD5 查重和删除重复文件的脚本组合。这证明“把网盘元数据放到本地再分析”有真实需求，但它们不是通用产品，也没有 POSIX 查询语义、自动发现官方本地数据库或稳定增量同步。

### 14.5 结论

PanFind 不应重复实现普通名称搜索、网盘客户端、WebDAV 或文件下载。差异化应严格集中在：

> 官方客户端本地元数据 -> 统一 POSIX 风格命名空间 -> 高级元数据查询。

## 15. 官方 API 与认证边界

百度已经提供官方开放 API/SDK，可以列目录并返回比本地数据库更丰富的元数据，包括某些创建时间字段。但公开桌面工具面临认证和密钥分发问题：

- 某些 OAuth 流程需要 `app_key` 和 `secret_key`；
- 开源桌面二进制无法真正保密内置 secret；
- 要求普通用户自行申请开发者凭据会显著增加使用门槛；
- 要求 BDUSS 或 Cookie 会增加安全风险和维护负担。

因此 MVP 使用官方客户端本地数据库，不依赖远端 API。未来可以增加可选的 `baidu-openapi` provider，由用户提供开发者凭据或在获得合适官方授权后启用，但不能硬编码秘密，也不能把 Cookie 登录作为默认方案。

## 16. MVP 范围和验收标准

### 16.1 第一阶段交付

1. Windows amd64、macOS amd64 和 macOS arm64 原生 Go CLI；
2. 自动发现百度网盘本地账号数据库，并支持列出和选择账号；
3. 只读加载 `file_meta`；
4. 构建内存命名空间；
5. 支持基础 `find` 谓词；
6. 支持文本和 JSON Lines 输出；
7. 提供 `status`、`capabilities` 和清晰错误；
8. 用真实的 18,000 多节点数据验证；
9. 提供合成数据和差分测试；
10. 提供前台 `watch` 的全量刷新、失败保留和原子发布；
11. README 必须准确描述当前安装方式、命令、兼容范围、隐私边界和已知限制。

### 16.2 最小可证明闭环

```bash

```

验收要求：

- 不修改数据库；

- 查询接近瞬时；

## 17. 建议的代码边界

当前采用单一 Go module，并按职责划分以下 package：

```text
cmd/panfind/          命令行入口
internal/app/         子命令编排、输出和退出码
internal/query/       Parser、AST、谓词、执行器和 GNU find 差分测试
internal/namespace/   标准化节点和不可变快照
internal/provider/    Adapter 接口、能力模型和账号发现类型
internal/baidu/       百度 filecache.db 适配器
internal/syncer/      变化轮询、合并窗口和原子快照发布
internal/output/      文本、-printf 和 JSON Lines 输出
internal/testkit/     合成树和测试辅助数据
```

不要因为未来可能支持多个网盘而过早做复杂插件系统。先用小而清晰的 Go interface 隔离数据源即可。快照由 builder 独占构造，发布后视为不可变，并通过 `atomic.Pointer` 原子切换查询可见 generation。

## 18. 风险和待验证问题

### 18.1 官方客户端结构变化

`filecache.db` 是官方客户端内部实现，不是稳定公共协议。客户端升级可能改变路径、表结构、字段语义、加密方式或访问限制。

应对方式：

- 按平台记录已验证的客户端版本、验证日期和对应 PanFind 提交；
- schema/version adapter；
- 启动时严格探测；
- 不认识的版本拒绝给出不可信结果；
- 保留可匿名提交的 schema 诊断信息；
- 建立版本兼容测试样本，但不得收集用户文件名等隐私数据。

### 18.2 字段语义不完整

尤其是创建时间、加入时间和移动后的时间语义。所有字段都需要标注来源和精确含义。

### 18.3 多账号

节点键已经组合 provider、account 和节点 ID，避免跨账号冲突。CLI 使用 `panfind accounts [--json]` 列出账号；只有一个账号时自动选择，多个账号时通过根路径后的 `--account <account-id>` 显式选择。第一版不把账号编码进 `baidu:/` 路径，从而保持查询根语法简单。

### 18.4 超大规模

当前验证规模只有约 18,000 节点。需要用合成数据验证：

- 10 万节点；
- 100 万节点；
- 深目录；
- 单目录大量子节点；
- 大规模移动和删除；
- 长时间高频数据库变化。

### 18.5 隐私

文件名、路径、哈希和时间均属于敏感个人数据。默认不上传遥测，不在错误报告中输出真实文件名。诊断命令应支持脱敏。

### 18.6 名称和许可证

- PanFind 是当前候选名称，正式发布前复核包名、仓库名和潜在商标冲突；
- Go 依赖的许可证兼容性需要在正式发布前复核；
- 项目许可证暂未最终决定，可优先评估 MIT 或 Apache-2.0。

## 20. 暂不决定的事项

以下问题留待正式开发和原型结果决定：

- 是否在前台 `watch` 之外增加常驻后台进程和 IPC；
- 是否完全不使用自己的持久化缓存；
- 首版是否记录 `first_seen_at`；
- Windows 和 macOS 后续是否增加安装器、代码签名与公证；
- 后续 Skill 放在主仓库还是独立插件仓库；
- GUI 是否永远保持独立于核心项目。

## 21. 当前共识

1. 这个项目解决的是真实、反复出现的问题，而不是为了使用 AI 而创造需求。
2. 市面上已有普通网盘搜索、第三方客户端和名称索引，但尚未发现等价的 POSIX 元数据查询工具。
3. 百度本地 `filecache.db` 已证明 MVP 在技术上有可行数据源和足够快的扫描性能。
4. 第一阶段不需要第二个 SQLite 数据库，先使用官方数据库快照和内存命名空间。
5. 每次启动和检测到变化时完整刷新；只有实测无法满足目标时才考虑增量更新。
6. 允许约 1 秒滞后，但必须保证快照完整和错误可见。
7. CLI 和 Query AST 是核心，AI Skill 是未来的自然语言入口。
8. 先把百度做稳，再验证夸克；不要提前为未知数据源过度设计。
9. 项目成功与否应以是否真实解决用户问题衡量，而不是以 GitHub Star 数量衡量。
